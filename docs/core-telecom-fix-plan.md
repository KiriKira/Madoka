# Core-Telecom 合并后的修复计划

2026-11-18，基线 `b976626`。先处理三项可能影响麦克风或系统通话生命周期的问题，再改接听和恢复。双讲问题可用现有版本独立取证。本文中的 P1、P2 表示审阅问题的优先级；原迁移计划的 P1、P2 表示交付阶段。实现依据见[代码审阅](core-telecom-call-quality-review.md)和[设备验证清单](core-telecom-validation.md)。

## 第一批：通话安全和清理

| 问题 | 修改位置和预期行为 | 可重复的验收 |
| --- | --- | --- |
| P1 系统静音观察失效后仍可能发送音频 | 在 CoreTelecomAdapter 中分开处理端点列表和静音流。静音同步丢失时立即关闭本地发送，继续接收；在通话页明确提示。安全静音作为独立条件，与用户静音、保持和业务授权取交集。在本次会话重新获得可信的系统静音状态后才撤掉该条件。若库无法可靠重订阅并读取当前值，保持安全静音并提供结束通话入口。 | 注入静音流异常和提前结束，验证外发轨关闭、接收继续；等待期间用户取消静音也不能重新送音。恢复、通话结束及端点列表单独故障各覆盖一次。 |
| P1 断开超时仍调用完成回调 | 在 TelecomDisconnect 和 CoreTelecomAdapter 中区分注册明确失败、平台确认断开和结果未知。未知时立即关闭媒体，由已有进程级通话任务继续管理系统断开和通知。合并同一通话的重复挂断，处理迟到的注册或平台回调。重试有次数和期限；预算耗尽后记录未确认状态并保留可操作的清理入口。仅在有可靠结束证据时通知 HostCallService 完成清理。 | 假平台分别模拟迟到注册、明确拒绝、调用超时、迟到成功和服务销毁。验证未确认时不提前撤掉通话服务、迟到成功只清理一次、旧回调不清掉新通话。设备再用 dumpsys 确认无残留。 |
| P1 初始化回放旧的媒体许可 | 在 RtcAudioSession 中让 native peer 发布、初始许可应用和后续保持／静音更新具有一致的顺序。避免在生命周期锁内执行可能阻塞回调的 native 创建和销毁。默认关闭音频，使用最新许可启用。 | 用屏障暂停初始化，在此期间触发保持、静音或结束再继续，断言旧许可不能重新打开音轨。另测正常恢复后用户静音仍有效。 |
| P2 验证记录口径 | 默认构建使用 legacy，显式传入 `-PcoreTelecom=true` 才启用新实现。旧后端的模拟器 UI 冒烟已通过。Core-Telecom 的挂断、系统接听、外呼地址、后台麦克风四项按迁移清单单独取证。 | 本次已订正[验证记录](core-telecom-validation.md)和[11 月 17 日复审记录](core-telecom-review-20261117.md)。每份后续设备证据注明提交、构建参数、API 级别和测试路径。 |

## 第二批：所有网络默认用已知通话版本接听

在 RtcCallEngine 的来电接听入口，沿用本地可接听检查和服务就绪检查。取当前节点、当前配对会话和同一 call_id 最近一次可信服务器快照的 `state_revision`，传给 RtcCallControl。快照若缺少合法版本则沿用现有读取路径，不猜固定版本号。该策略用于 Wi-Fi、移动网络和中继通话，无需 RTT 判断或额外探测。

1. 有可用版本就直接 POST accept，正常命中时协议序列只有一个 POST，省去一次 GET。成功响应更新快照。
2. 明确收到 `409 CALL_STATE_CONFLICT` 后才重新 GET 并判断是否仍有资格接听；仍可接听才用新版本提交。超时或可重试的 5xx 复用完全相同的操作 ID、版本和请求体，遵守现有总尝试预算。明确拒绝、撤权、过期、其他主机已接和终态按各自语义收尾。重复点击共享同一个在途操作。
3. 用录制请求序列的测试覆盖快照命中、缺失、冲突可重试、冲突时已被抢接、响应丢失和切换配对节点。确认一次业务接听、一次媒体准入，旧请求不会复活已结束通话。
4. 记录同一通话从点击、平台接听、前台服务就绪、accept 成功、媒体准入、offer 到首个有效接收音频帧的单调时间。比较冷／热缓存、普通／高 RTT 下的 P50、P95 和接通率。已有响铃期 TURN 预取及网络维度的探测缓存；若中继阶段仍显著占时，在配置与凭据有效且满足中继策略时复用。验证仅 TURN 可达、首次使用、换网和凭据过期。预取仅在来电期间执行，响铃结束即取消。

## 第三批：弱网恢复与待机功耗一起验收

现有服务层宽限约 30 秒，媒体层的部分读失败或断连路径约 10 秒结束，ICE FAILED 还可更早结束。第一步在**当前已建立的通话**内统一决策。使用通话 ID、代号和单调截止时间标识一次恢复，在同一轮内合并网络变化、信令和 ICE 事件。重复事件不能延长截止时间。授权有效时优先尝试保留原媒体连接，授权失效、明确挂断或到期即关闭；保持与静音在整个恢复期间持续生效。

若原路径确需替换，再由 Madoka、Homura 和信令服务协商支持 ICE restart。按媒体代号隔离 SDP、候选、结束标记和迟到回调；设置次数、时间和并发上限。旧节点按既有协议结束或恢复。按两步分别交付和测量。

**保留现有的弱网省电修复。** 活跃通话的恢复复用现有调度与唤醒合并机制，每通最多一个在途恢复。挂断、撤权、被新通话替换或超时后取消重试、探测和监听，并释放该次恢复持有的锁。快速重拨不能继承旧定时器。待机继续按现有状态决定是否持锁。兼容模式空闲轮询失败时退避最长 60 秒，Reception v2 空闲使用 15 分钟的非唤醒定时器；已监听到无网且空闲时跳过请求。保留 WebSocket 重连抖动及稳定 60 秒后才重置退避的规则。质量统计沿用通话中的采样，禁止新增后台保活、固定频率探测或为恢复增设周期闹钟。[RTC 调度](../app/src/main/java/com/callagent/host/calls/RtcCallEngine.kt) · [WebSocket 重连](../app/src/main/java/com/callagent/host/background/HostBackgroundService.kt)

| 对照场景 | 验收方式 |
| --- | --- |
| 熄屏待机、无网、弱网持续失败、WebSocket 反复开闭 | 在同设备、同配置、相同网络事件序列和等长观察窗下，对照基线。分别覆盖 v2 和兼容模式。时钟可控的测试要求空闲请求、闹钟及唤醒次数不增加，失败退避不被短时开连重置；恢复网络后仍能收到一次有效来电提示。 |
| 通话中短断、Wi-Fi 与蜂窝互切、仅信令不可达、推送和网络提示重复到达 | 比较恢复成功率、丢音时长、请求与重试数。挂断后继续观察至少一个完整 v2 空闲周期，确认该通话新增的任务、探测和唤醒锁归零，调度回到原待机策略。 |
| 真机功耗 | 用 StandbyDiagnostics 的 HTTP、poll、wake-lock 计数与系统 batterystats 的唤醒闹钟、实际部分唤醒锁时间和耗电对照。比较每小时数据，在波动时重复同一场景；若空闲出现额外周期唤醒、持续持锁或可重复的功耗上升，暂停推广恢复改动。保留正常来电接通率作为对照。 |

回归套件包括 RtcCallEngineStandbyTest、RtcCallEngineOfflineTest、RtcSignalingWakeLeaseTest、RtcSleepyListeningTest、CoalescedCallPollTest 和 HostWakeRecoveryTest。新增测试只补跨状态竞态、重复事件、重试预算和终态释放。[既有待机验证](background-standby-power-progress.md)

## 双讲断续：按音频方向定位后再改

在同一设备和网络上依次做内置音乐来电、真实 SIM 来电，对比单方发声和双方重叠的相同时间窗，记录网关机型配置、采集源、耳机／听筒／免提路由。若仅 SIM 来电复现，Homura 有原始语音且双讲段 `gates:echo` 增长、Madoka 丢包和 `concealed_pct` 保持低位，优先修网关的逐帧回声误判。对确认无回灌的采集路由按机型绕过门控；有回灌的路由评估迟滞和渐变衰减。用双讲词尾完整度、对方听到的自身回声及纯单讲表现共同验收。若网络丢包隐藏或 PCM 欠载计数随断续增长，分别处理传输路径或网关送帧时序。[两端日志与判断依据](core-telecom-call-quality-review.md)

每批记录独立提交和验证结果。保留两个后端的构建、单测和 lint；静音、保持、挂断、切网与熄屏待机补相应设备证据后，再决定 Core-Telecom 默认启用时间。
